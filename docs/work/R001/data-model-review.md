## 1. "DB" ของโปรเจกต์นี้คืออะไร

ไม่มีฐานข้อมูล ไม่มีเซิร์ฟเวอร์ ไม่มีตาราง — เป็น **JSON ก้อนเดียว 1 คีย์** ใน `localStorage` ของเบราว์เซอร์ผู้ใช้

```text
คีย์: sabayjai-pantry          ~6,507 ไบต์ · schemaVersion 2 · 8 คอลเลกชัน
├─ schemaVersion : 2
├─ meta          : { seededAt, updatedAt }
├─ locations[5]  : { id, name, createdAt }
├─ categories[4] : { id, name, createdAt }
├─ units[14]     : string[]                        ← ไม่มี id (11 สำเร็จรูป + 3 ที่ seed เพิ่ม)
├─ products[10]  : { id, name, unit, categoryId|null, note,
│                    createdAt, updatedAt }        ← ไม่มีจำนวน (ชื่อ+หน่วยซ้ำไม่ได้)
├─ lots[10]      : { id, productId, locationId, quantity, usedUpQuantity,
│                    expiryDate|null, createdAt, updatedAt }
│                                                  ← ยอดที่ทยอยหักได้ทีละส่วน + ยอดก่อนหมด (D10)
├─ movements[12] : { id, lotId, type, delta, balanceAfter, at, note|null }
└─ shopping[2]   : { id, text, createdAt }
```

**ผลตามมา (ควรรู้ก่อนตัดสินใจ):**

1. ข้อมูลอยู่กับเครื่องนั้นเครื่องเดียว — เปิดคนละเครื่อง/คนละเบราว์เซอร์ = คนละชุดข้อมูล ไม่มีการซิงก์ (ตรง NFR 4.3)
2. ล้างข้อมูลเบราว์เซอร์ / ใช้โหมดไม่ระบุตัวตน = ของหายทั้งหมด (ไม่มีที่อื่นเก็บ) — **แต่ในแอปเอง ของไม่หายเงียบแล้ว:** ก่อนรีเซ็ต/ก่อนพบข้อมูลที่อ่านไม่ได้ ระบบเก็บสำเนาเดิมไว้ที่คีย์ `sabayjai-pantry.backup` และกู้คืนได้จาก `#/settings` (D8 · §3 ข้อ M2)
3. ทั้งก้อนถูกเขียนใหม่ทุกครั้งที่แก้ 1 รายการ (~6.3 KB ตอนนี้ — ยังไม่มีปัญหา แต่จะโตตามจำนวนของ **และตามจำนวน movement ที่ไม่ถูกลบ** ดู F8)
4. `schemaVersion` **มี migration จริงแล้ว**: `migrate()` แปลง v1 → v2 อัตโนมัติ (ดู §3 ข้อ M1)

## 2. โครงข้อมูลจริงที่รันอยู่ (ตัวอย่างสดจาก `createSeed()`)

```json

    { "id": "mv-lot-butter-1-out", "lotId": "lot-butter-1", "type": "out",
      "delta": -1, "balanceAfter": 0, "at": "…", "note": null }
  ],

  "shopping": [ { "id": "seed-shop-1", "text": "น้ำตาลทราย", "createdAt": "…" } ]

```

**จุดที่ต้องสังเกตในตัวอย่างข้างบน**

- `prod-butter` **ไม่มียอดจำนวนเลย** — ยอดอยู่ที่ `lots[].quantity` เท่านั้น (นี่คือหัวใจของ v2)
- "ใช้หมดแล้ว" ของเนยจืด **ไม่ใช่แถวพิเศษ** — คือ `lot-butter-1` ที่ `quantity: 0` และมี movement `in` → `out` ต่อกันให้อ่านย้อนได้ว่าเดิมมี 1 ก้อน
- `lot-butter-1` มี **`usedUpQuantity: 1`** เก็บไว้ที่ล็อตตรง ๆ (D10 · คำตอบ ข.) — จอ `#/used-up` ของ R005 อ่านเลข "จำนวนเดิม" ได้ทันทีโดยไม่ต้องไล่ประวัติ · ล็อตที่ยังมีของอย่าง `lot-milk-1` เก็บ `0`
- `units` มี 14 ตัว: 11 ตัวตาม requirement ข้อ 5.2 + `ถ้วย` (โยเกิร์ต) · `ก้อน` (เนยจืด) · `ลูก` (มะนาว) ที่ seed เพิ่มเองผ่าน `ensureUnit()`
- movement เก็บ `at` เป็น **ISO timestamp** แต่ `lots[].expiryDate` เป็น **วันที่ล้วน `YYYY-MM-DD`** — ตั้งใจ (วันหมดอายุไม่ต้องมีเวลา)

## 4. ข้อสังเกตที่ยังเปิดอยู่ (F1 · F5 · F6 + F7–F8 ใหม่)

> F2 · F3 · F4 ของฉบับ v1 **หายไปพร้อมสคีมา v2** — ย้ายไปภาคผนวก §8 พร้อมคำอธิบายว่าทำไม

### F1 · `units` ไม่ใช่ลิสต์ที่ครบ — หน่วยถูกใช้จริงแต่ไม่มีในลิสต์สำเร็จรูป
`units` มี 14 ตัว แต่ 11 ตัวแรกคือชุดสำเร็จรูป อีก 3 (`ถ้วย` · `ก้อน` · `ลูก`) ถูกเพิ่มเข้ามาเพราะของใน seed ใช้
**ผลคือ:** เปลี่ยนชื่อหน่วยไม่ได้ (ของเดิมไม่ตาม) · ลบหน่วยไม่ได้ · ลิสต์ยาวขึ้นเรื่อย ๆ ไม่มีวันหด
**สถานะ:** ✅ **ปิดเป็นคำตัดสิน D1 = คงเป็นข้อความอิสระ** (ยอมรับข้อจำกัดนี้)

### F5 · วันที่ใน seed ไม่ได้มาจากวันเดียวกัน (ตั้งใจ แต่เดิมไม่ได้บันทึกเหตุผล)
`meta.seededAt` = วันนี้ · `shopping[].createdAt` = ย้อนหลัง 1 และ 3 วัน · ล็อตที่ใช้หมดแล้ว = ย้อนหลัง 2 และ 5 วัน (movement `in`/`out` ใช้วันเดียวกันทั้งคู่)
**ผลคือ:** เดโมดูมีชีวิตชีวา แต่กดรีเซ็ตเมื่อไรวันที่จะเลื่อนตามทุกครั้ง
**สถานะ:** ✅ **ปิดด้วย D5 = ก. (2026-10-16)** — คงวันที่ย้อนหลังไว้ (shopping 1/3 วัน · ล็อตที่ใช้หมดแล้ว 2/5 วัน) แล้วบันทึกเหตุผลไว้ใน `docs/design/sabayjai-pantry.md` ข้อ 2.5 · วันที่ยังเลื่อนตามวันกดรีเซ็ตอยู่แล้ว

### F6 · `normalizeState()` ไม่ตรวจรูปร่างของข้อมูล แค่เติมคอลเลกชันที่หาย
ถ้าข้อมูล **parse ได้** แต่ข้างในเพี้ยน (เช่น `lots[3].quantity` เป็นข้อความ หรือ `products[1]` ไม่มี `unit`) จะถูกโหลดเข้ามาใช้ตามนั้นแล้วพังที่หน้าจอทีหลัง
**ผลคือ:** JSON ที่พังบางแบบไม่ตกไปที่ "คืน seed" ที่ออกแบบไว้ → เจออาการเพี้ยนแทนการรีเซ็ต
**สถานะ:** ✅ **ลงมือแล้ว (D9 · 2026-10-16)** — `normalizeState()` ตรวจรายฟิลด์ครบทุกคอลเลกชัน (ตัด `id` ซ้ำ · ข้อมูลกำพร้า · ยอดที่ไม่ใช่ตัวเลข · วันที่ที่ไม่มีจริง · `type` ที่ไม่รู้จัก → `adjust` · รหัสที่หาย → ออกใหม่) แล้ว `console.warn` สรุปว่าซ่อมอะไรไป · มีเทสต์ใน `storage.test.js` และตรวจซ้ำบนเบราว์เซอร์จริงด้วยข้อมูลที่จงใจทำให้เพี้ยน

### F7 · 🆕 ยอด "จำนวนเดิม" ของของที่ใช้หมดแล้ว ไม่ได้เก็บไว้ในล็อต
ล็อตเก็บแค่ยอดปัจจุบัน (0) ไม่ได้เก็บว่าก่อนหมดมีเท่าไร · ตัวเลขนั้นต้องอ่านจาก **movement ล่าสุด** (`out`/`discard`) หรือให้ R005 จำยอดก่อนหักไว้ในหน่วยความจำ
**ผลคือ:** แถวใน `#/used-up` (R005) ต้องเลือกว่าจะอ่านเลขจากไหน · จำนวนที่โชว์ตอนกด "ย้อนกลับ" 5 วินาทีต้องเป็นยอดที่จำไว้ ไม่ใช่ยอดที่อ่านจากล็อต
**ข้อสรุป:** ✅ **ปิดด้วย D10 = ข. (2026-10-16)** — **เพิ่มฟิลด์ `usedUpQuantity` ให้ล็อต** (ไม่ใช่ใช้ movement ล่าสุดเป็นแหล่งเดียวเหมือนข้อเสนอเดิม) · เหตุผลจากเจ้าของโปรเจกต์: มีทั้งยอดรวมและยอดล็อตอยู่แล้ว การมียอดเดิมอีกฟิลด์ไม่แปลก และการอัปเดตเป็นหน้าที่ของโค้ด · กันค่ามั่วด้วยคำสั่ง `recalculateUsedUpQuantities()` (ไล่ประวัติแล้วคำนวณใหม่) + ปุ่มใน `#/settings`
**ความหมายที่ล็อกไว้:** `usedUpQuantity` = **ยอดก่อนที่ล็อตนี้จะหมด** (ยอดตอนก่อนหักครั้งสุดท้าย) — ตรงกับค่าที่ R005 ต้องใช้ตอน undo · ล็อตที่ยังมีของเก็บ `0`

### F8 · 🆕 ล็อตที่ยอด 0 และ movement **ลบไม่ได้เลย** — ข้อมูลโตขึ้นเรื่อย ๆ

## 6. ตัวอย่างก่อน/หลัง ของข้อที่ผลกระทบสูง

### D1 · หน่วย — ถ้าเลือก ข.
```jsonc
// ก่อน (ตอนนี้)
"units": ["ชิ้น","กล่อง",…],

```
**ผลกระทบถ้าเลือก ข.:** แก้ `seed.js` · `db.js` · `validate.js` · `selectors.js` · views ที่แสดงหน่วย · เทสต์ที่อ้าง `unit` เป็นข้อความ — **แต่ยังไม่ต้องเขียน migration** เพราะยังไม่มีข้อมูลผู้ใช้จริง
**ถ้าเลือก ก. แล้วเปลี่ยนใจภายหลัง (หลัง R009 deploy):** จะต้องเขียน `migrate()` ที่แปลงข้อมูลในเครื่องคนอื่นให้ครบทุกเครื่อง ไม่ทำแล้วของหาย

### D8 · กันข้อมูลหาย — ถ้าเลือก ก.

```json
"sabayjai-pantry"          // ของที่ใช้อยู่ — อ่านไม่ได้ → ย้ายไปคีย์นี้ก่อน
"sabayjai-pantry.backup"   // สำเนาของเดิม + วันที่ → #/settings แสดงปุ่ม "กู้คืนข้อมูลเดิม"
```
**ทำไมควร:** ผู้ใช้กรอกของในบ้านตัวเอง ของหาย = เสียหายจริง · ต้นทุนราว 5 บรรทัด + เทสต์ 2 ตัว

### D10 · จำนวนเดิมของของที่ใช้หมดแล้ว — สองทางเลือก
```jsonc
// ก. อ่านจาก movement ล่าสุด (ตอนนี้ทำได้อยู่แล้ว)
//    lot-butter-1 { quantity: 0 }
//    movements: … type 'in' delta +1 → type 'out' delta -1   ⇒ "เดิมมี 1 ก้อน"

"lots": [{ "id": "lot-butter-1", "quantity": 0, "usedUpQuantity": 1 }]
```

**ทำไมเสนอ ก.:** ไม่เพิ่มความซ้ำซ้อน (ข้อมูลชุดเดียวคือ movement) และวันที่ของ "ใช้หมดเมื่อ" ก็มาจาก movement อยู่แล้ว · เสียที่ต้องอ่าน movement ทุกครั้งที่วาดมุมใช้หมดแล้ว (ข้อมูลเล็กมาก)
